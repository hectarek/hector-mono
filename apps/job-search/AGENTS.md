# AGENTS.md — job-search

> Read the root [AGENTS.md](../../AGENTS.md) first. This file only covers app-specific context

## Overview

A private job search workspace. Its owner and Claude both keep it current, and each day it shows what needs a decision and what's due. Claude works in it through the app's MCP endpoint, with page tools (WebMCP) in its own browser profile as the fallback. Clean architecture on recipes' pattern: [../../docs/clean-architecture.md](../../docs/clean-architecture.md), with `apps/hectors-recipes` as the reference.

[docs/build-plan.md](docs/build-plan.md) is the initial spec: requirements, decisions (KTDs) and units. What's done and what's left lives in Hector's private task tracker, one task per unit under the same U number: start from the unit's task, then follow the spec's How to work from this spec. [docs/ux-plan.md](docs/ux-plan.md) is the usability pass's initial spec, worked the same way under UX numbers: the audit of 2026-11-06, its findings, and the units that fix them. Setting up Claude's access, the endpoint and its browser: [docs/agent-access.md](docs/agent-access.md).

## Privacy (R24)

- The repo is public. Code, tests, fixtures, docs, tool descriptions, screenshots, commit messages and PR text use fictional or generic data. Companies, people, targets, pay and strategy live only in the app's database or Hector's private docs. A task that would put a specific of the search into the repo stops, and that content goes to one of those two places.
- Signed-out pages, the private screen and the metadata carry the generic name "Job search", never a person's name. Every page is `noindex` (the root metadata) and `app/robots.ts` disallows everything.

## Stack

- Next.js 16, React 19, Tailwind CSS, shadcn/ui via `@repo/ui` with its `job-search` theme (Saira, Atkinson Hyperlegible Next and Mono; UI Rules)
- Neon Postgres via `@neondatabase/serverless`, Drizzle ORM, generated migrations in `db/migrations/`
- Auth via `@neondatabase/auth` (Better Auth powered)
- DI via `@evyweb/ioctopus`

## Differences from recipes

The infrastructure is copied from recipes, not shared (docs/build-plan.md KTD1). Four things differ on purpose:
- **No redirects on the tool path (KTD4).** A redirect navigates the page, so a page tool gets nothing back and Claude can't confirm a write. `proxy.ts` lets a request carrying the `Next-Action` header past its signed-out redirect, both with no session cookie and when the session-cache refresh finds the session ended, so the action answers `unauthenticated` itself. Recipes' proxy redirects them. Actions call `revalidatePath`, never `redirect`, and return an envelope (Backend Rules).
- **Environments (KTD17).** The local `.env` and preview deploys use the Neon test project only. Production values live only in Vercel's Production environment, as sensitive variables, and never pass through a Claude session. Recipes uses its production database locally; this app doesn't, because `.worktreeinclude` copies `apps/*/.env` into every worktree.
- **Logging (KTD20).** Logs carry error classes, codes and record ids, never field values. Recipes logs `err.message`, and a failed query's message carries its parameters (names, notes, pay). Here the transaction manager, `BaseRepository.handleError`, `toActionError` and the auth route log only what `loggable(err)` (`src/entities/errors/loggable.ts`) gives: the error's class and the first code down its cause chain, such as Postgres's SQLSTATE. The auth route logs Neon's failed answers by status and path, never the body.
- **A session that can't be read (U2).** `NeonAuthService` throws when Neon answers `getSession` with an error; recipes' copy returns null, as if signed out. The auth route lets signed-out requests through to Neon (to sign in), so a failure must never read as signed out.

## Cache Components

Recipes' rules carry over ([its AGENTS.md](../hectors-recipes/AGENTS.md#cache-components)):
- `export const dynamic`, `revalidate` and `dynamicParams` fail the build. A page that reads the session, its address or the database in its body gets a `loading.tsx` in its own folder.
- Read the session first, then the clock: Today does (`todayIn` runs at request time).
- A page without a `loading.tsx` puts what it reads at request time inside `<Suspense>`: the welcome screen's Sign in, the auth pages' form and the private screen's account. So does the `(main)` layout's `SessionChrome`.
- Only a real request reads the session or the database. `getPageActor`, the auth pages' form and the private screen's account first `await connection()` (`next/server`), where a prefetch or a prerender stops, so a new session read goes behind one too. Partial prefetching renders each route's App Shell at request time, and without the stop a prefetch ran the page's session and database reads until its render ended. On Vercel the reads still running then failed and logged errors, and so did Neon Auth's session fetch; locally, `next start` let them finish (2026-11-06). Behind `connection()`, `next build` reaches neither, so `experimental.hideLogsAfterAbort` went.
- A client component above a page's `loading.tsx` (the shell) reads the path (`usePathname`, `useSelectedLayoutSegment(s)`) only under its own `<Suspense>`: prerendering a route with params (`/jobs/[id]`) hangs on it, and outside a boundary `next build` fails ("encountered URL data `usePathname()` in a Client Component outside of `<Suspense>`"). `next dev` and the tests don't show it and CI doesn't build, so run `next build` after changing the shell. `app-nav.tsx` does this for the menu's mark, the top bar's name and the tab's title.
- `next build` needs `NEON_AUTH_BASE_URL` and `NEON_AUTH_COOKIE_SECRET` set (`lib/auth/server.ts` throws at import without them), but nothing at build time reaches Neon or the database, so placeholder values build. The one exception is a production build on Vercel, whose migration check reads production's migrations first (Environments). It does fetch the fonts from Google (`next/font/google`), which fails inside Claude Code's sandbox even with `allowed_domains` (Turbopack's fetch doesn't go through the sandbox's proxy, 2026-11-10), so run the build outside it. There it reads `.env`, which holds test-project values only (Environments).

## Auth Rules

- Two accounts use the app (KTD2): Hector's is the `owner` and Claude's the `agent`, and both act on Hector's rows. Who's acting comes from `app/_lib/current-actor.ts`, as `{ actor, ownerId }`: `getPageActor()` in pages and the session chrome, `getActionActor()` in server actions. Both go through `IResolveActor` (`src/application/use-cases/access/resolve-actor.ts`), except inside an MCP endpoint call, where `getActionActor()` answers the actor the token resolved to (`withTokenActor`) and reads no session.
- Identity goes by user id, never email: `OWNER_USER_ID` and `AGENT_USER_ID`, read by `di/modules/access.module.ts` (tests pin `MockAuthService`'s `TEST_ACCOUNTS`). A missing or malformed id refuses every session, and the first refusal logs it.
- Any other signed-in account is refused before anything is read. `getPageActor` redirects it to `/private`, which shows its email and Sign out and nothing else; with no session it throws into `app/error.tsx` (the proxy has already sent signed-out visitors to the welcome screen). `getActionActor` never redirects (KTD4): it throws `NotAllowedError`, which the action answers as `not-allowed`, or `UnauthenticatedError` when no one is signed in.
- A layout doesn't stop its pages from rendering, so every page calls `getPageActor` itself. The `(main)` layout's `SessionChrome` only decorates: Claude's banner and the page tools' registrar, streamed inside `<Suspense>`.
- The auth route passes `GET get-session` and `POST sign-out` from any session (R21: Claude's session can only read itself and sign out). Neon's OAuth steps that authorize the MCP endpoint (`POST oauth2/continue`, `POST oauth2/consent`, `GET oauth2/public-client`) pass from Claude's session alone, and any other gets 403 `not-allowed` (R21 as revised, KTD22). Every other endpoint (update-user, change-email and the rest) reaches Neon only from Hector's session or from no session (signing in). Claude's session gets 403 `human-only`, any other account 403 `not-allowed`, and a session that can't be read gets a 500.
- `IAuthenticationService.getSession()` is null only when no one is signed in, and throws when the session can't be read (Differences from recipes). The private screen reads the email through it. `lib/auth/server.ts` is only for the auth route, the auth page and `NeonAuthService`.
- `proxy.ts` is recipes' cookie check and session-cache refresh ([../../docs/proxy-auth-research.md](../../docs/proxy-auth-research.md), 2026-09 addendum), plus the `Next-Action` pass-through above. Signed-out pages go to `/welcome?redirectTo=<path>`; the welcome and auth pages honor only same-app paths (`app/_lib/safe-redirect.ts`).
- Sign-up is off in the UI: `AuthProvider` sets `signUp={false}`, so the sign-in form has no link to it and its view sends visitors to sign in, and the welcome screen offers only Sign in. Both accounts are created before first use, and Neon's own setting is to close sign-up once they exist (the plan's H2). Hector deferred that step on 2026-10-28 with the rest of the lock-down, so until it's done an account that signs up some other way sees only the private screen (R23).
- Safari can't sign in on `http://localhost` (Neon Auth's cookies are always `Secure`), as in recipes.

## Backend Rules

- **Actions answer an envelope (KTD4).** Each action in `app/actions/<domain>.ts` returns `ActionResult<T>` (`app/actions/shared.ts`) through `answer(op, fallback, run, pages?)`. It runs the action's work and answers `succeeded(data)`, which is `{ ok: true, data, asOf }`, or `toActionError(err, actionLogger(op), fallback)`, `{ ok: false, code, message, fields?, current? }`. On success it revalidates the paths `pages(data)` lists, none for a read, so an action never calls `revalidatePath` itself, and never `redirect`. The mapping: `InputParseError` → `validation` (with `fields`), `UnauthenticatedError` → `unauthenticated`, `NotAllowedError` → `not-allowed`, `HumanOnlyError` → `human-only`, `NotFoundError` → `not-found`, `ConflictError` → `conflict` (with `current`, the record as it is now), `DuplicateError` → `duplicate` (with `current`, the job that holds the posting), anything else → `unexpected` with the action's own message. A page tool's call can also get `reload-needed` or `unexpected` from its wrapper (Page Tools). `calendar-disconnected` arrives with the calendar (U13).
- **Every write records its change (R19, KTD7).** A write action takes the page tool's name as its last argument, `(input, tool?)`, and builds its `ChangeContext` (`{ actor, ownerId, tool? }`, `src/entities/models/activity.model.ts`) with `changeContext(tool)` (`app/actions/shared.ts`): the session's actor, and the name, checked as input (`toolNameSchema`: snake_case, at most 30 characters), so a bad one is `validation` before anything is written. Inside the write's own transaction, the use case calls `recordChange` (`src/application/use-cases/activity/record-change.ts`) with it. Give `before` and `after` the fields the change touched; it keeps only those whose values differ. The `activity` table is append-only: never update or delete a row.
- Claude's working sessions are in the log too, with no table of their own: `start_session` writes one `created` row per start, record kind `agent-session` and a fresh id, and answers with the changes from the actor's previous start (inclusive) to this one, newest first (`start-session.use-case.ts`). `list_activity`'s `record` filter without an `id` lists every record of a kind.
- A read that has to see the write's own rows runs inside its transaction: pass it the `tx`, as `start-session.use-case.ts` does with `activityRepository.list(ownerId, filter, tx)`. Outside it, Postgres doesn't see the uncommitted rows, and PGlite waits on its one connection.
- **Human-only operations check first (R21, KTD3).** Moving an archived job back to an open status (`reopen`), changing an archived job's posting link (`relink`), deleting anything, editing a note (Claude's notes only append), connecting or disconnecting the calendar and changing settings: the use case calls `requireHuman` (`src/application/use-cases/access/require-human.ts`) before its own transaction opens. Anyone but Hector gets a `refused` row, written in a transaction of its own so it stays, and `HumanOnlyError`.
- A record that keeps a history adds its kind to `recordKindSchema` (`activity.model.ts`), and its page mounts `<RecordHistory record={{ kind, id }} />`, which shows the latest 50 changes (Hector kept the cap, 2026-10-26). The owner's settings are one record, kind `settings`, whose id is the owner's.
- **The search season (R12 as revised 2026-11-10, U20)** is part of the settings: `season_start` and `season_finish`, both or neither and the finish after the start, and `season_checkpoints`, a JSON list of at most three `{ on, name }`, all checked by the table too. The form sends its three checkpoint rows. `updateSettingsSchema` leaves a blank row out, and checks the rest: each named in at most 40 characters, on a day between the start and the finish, no two on one day. Its messages name a checkpoint by its row, and the season is saved with its checkpoints in date order. The history logs the checkpoints as one line ("2026-11-13 Portfolio live; …"), since it shows an object as JSON. `get_settings` and `get_today` answer the season, null until it's set. `src/entities/season.ts` works out its legs (`legsOf`, one to each checkpoint and one to the finish) and where today falls (`placeOf`). A leg runs from its first day to the day before it ends, so a checkpoint's day is the next leg's first, and the last leg holds the finish's day.
- A screen or tool input gets a label in `FIELD_LABELS` (`app/_lib/field-labels.ts`, which the forms import too): a validation message names only listed fields, and prefixes the label unless the message already starts a word with it. `id` and `updatedAt` are listed, since a page tool sends them. A record's history names every field, in words when it has no label (`nextStep` is "Next step").
- **A change is made against what was read (R22, KTD15).** It sends the `updatedAt` read with the record (an ISO time, `timeSchema` in `input.model.ts`, beside the shared date, text and link schemas), and the use case reads the record with `getForUpdate` (`select … for update`, so it stays locked to the write), compares the two in JS and throws `ConflictError(current)` on a mismatch, as `save-company.use-case.ts`, `update-settings.use-case.ts`, `update-job.use-case.ts` and `edit-note.use-case.ts` do. A status move takes an optional `updatedAt` the same way, which the daily run sends (KTD24). A change that sets what's already there writes and logs nothing. `updated_at` columns keep milliseconds (default `date_trunc('milliseconds', now())`, a JS Date's precision), and each update moves the value on at least a millisecond (`greatest(…, updated_at + interval '1 millisecond')`, the mocks the same), so two changes in one millisecond still conflict.
- A form keeps the record it opened on and sends only the fields typed since, so a field someone else changed meanwhile keeps their value. On `conflict` it stays open on `current` with what was typed kept and lists what changed (`editedFields` and `rebased`, `app/_lib/form-changes.ts`), and the next save goes against `current`'s `updatedAt`. A record's form gets all of this from `useRecordForm(record, fieldsOf, isRecord)` (`app/_lib/use-record-form.ts`): the record it opened on, the fields as typed, `edited`, `save(run, onSaved)` with the rebase on a conflict, `reopen` for a form that stays on its page (settings), and the `changes` its `ConflictNotice` lists. Given a record with another id in the same place (the next task on Today's board), it starts over on that record, so it can't save to the one it held (2026-11-07).
- Names that compare loosely keep a key column the entity computes: `companyNameKey` (case and punctuation ignored) for the soft duplicate warning and `find_companies`, `sourceNameKey` (case and runs of spaces) under `lead_sources`' unique index, so `add_source` answers with the source already listed. Keys and names sort with `collate "C"`, by code point as the mocks sort, so the two backends agree.
- **Jobs and the ranked list (R20 as revised 2026-11-10, R27, KTD8, KTD23).** There's no review queue: a job Hector or Claude adds (`add_job`, `create-job.use-case.ts`) starts in verify with no next step unless one is given, on the ranked list at once. Claude's needs its posting's link and its reason, whatever the entry point (KTD3), and may carry the posting's date (`postedOn`) and the sweep's fit score (`score`, 1 to 10). The list is the jobs in verify and target (`TO_APPLY_STATUSES`), ordered by `src/entities/rank.ts` on every read (`ranked-list.ts`: `listToApply` reads the candidates, and the rank sorts them with Hector's pay floor from settings): pinned first, the latest pin first, then target, then by priority (score, company tier, the posting's age, pay against the floor), the expired left out. Nothing about the order is stored. `find_jobs`' `to-apply` and Today's apply next read it; `pin_job` (`pin-job.use-case.ts`) pins or unpins a job not yet applied to. Not for me is `close_job` as skipped with a reason (`not-for-me.tsx`). An archived job keeps its posting: a new job, or a new posting link, takes the owner's posting lock (`lockPostings`, a `pg_advisory_xact_lock`) before it checks for a duplicate posting (`posting-link.ts`'s key, under a partial unique index), archived jobs included, so two writes at once settle one at a time. `DuplicateError` answers `duplicate`, its `current` the job that holds the posting, and its message says when that job is archived (`job-checks.ts`). Only Hector moves an archived job back to an open status or changes its posting link (`move-job` and `update-job` call `requireHuman` before their transactions; a job archived in between conflicts instead). A job's write reads its company locked (`requireCompany`), so a company's delete and a write that names it settle one at a time.
- 0011 moved the queue's jobs onto the list, and 0012 dropped the queue's columns (`review_state`, `dismiss_reason`, `dismiss_note` and `settings.pending_cap`): the second of a drop's two PRs, after hectarek/hector-mono#111 took them out of `db/schema.ts` (Environments). Claude's reason lives in `proposal_reason`, which the code reads and writes as `reason` (`columnsOf` in `jobs.repository.ts`).
- **The daily run (KTD24)** archives each job that left the list untouched (unpinned, in verify or target, its `postedOn`, else `foundOn`, more than 21 days old in Eastern time) as skipped, "Not picked in time" (`EXPIRED_REASON`), by the actor `system`. `archive-expired.use-case.ts` moves each through `move-job` against the `updatedAt` it read, so a job pinned or changed meanwhile conflicts and waits for the next run, and a second run finds nothing. Vercel's schedule (`vercel.json`'s `schedules`, a path target: POST at 5 AM `America/New_York`) calls `app/(api)/api/cron/archive-expired/route.ts` with `Authorization: Bearer <CRON_SECRET>`; with no secret set, or any other token, the route answers 401 and does nothing. It acts for `OWNER_USER_ID` (`archive-expired.controller.ts`), as no one is signed in. Schedules run on production only. The list's read leaves an expired job out whether or not the run has happened.
- **A status move is a pure rule and two rows (R2, R3, KTD7).** `job-lifecycle.ts` says what a move sets (applied-on, the new stage's next step from `stepAfterMove`, none at applied, a closing's cleared one; R3 as revised 2026-11-07 in UX9 and 2026-11-09). A move to an open status can give its own `nextStep` and `nextDate` instead: a step alone keeps the stage's date, no step clears the date, and a null date is a week out (`withGivenStep`). `move-job.use-case.ts` writes the job, its dated `job_status_changes` row and its history in one transaction. A move to the status it holds writes and logs nothing, so a retried move never counts twice. `set_job_status` takes open statuses and `close_job` closed ones with a reason. The screens and `find_jobs` call the closed statuses together Archived (`status: "archived"`), so `closed` is the one status, the posting's (the UX plan's Q6); the code keeps `CLOSED_STATUSES` for the group. Claude sets applied-on only with a move: `update_job` refuses it from Claude with `validation`.
- **A next step always carries a date (R1 and R7 as revised 2026-11-07, the UX plan's Q1).** Every use case that writes a step (`create-job`, `update-job`, `add-person`, `update-person`, `log-interaction`) passes the change through `withStepDate` (`src/entities/next-step.ts`) before comparing it with the record: a step left with no date is dated a week from today, whoever writes it. A change that sets neither the step nor the date leaves them alone, so an edit elsewhere never dates an old step the import left undated (UX7's pass dates those). A new job given neither has no step: the ranked list is where it waits (R1 as revised 2026-11-10). A test that needs an undated step writes it through the repository inside a transaction (`app.repos`, or the container's `IPeopleRepository` in a screen test), as the import did.
- A job names its lead source by name, found ignoring case or added and logged (`sources/source-named.ts`, which `add_source` shares). Notes are records of their own in the log (kind `note`), pointing at their job or person by kind and id (a person's since the UX plan's UX8), and a note's change names its record (`noteOn`: `jobId` or `personId`). A job's delete takes its notes and status moves with it, a person's their notes, and `add_note` reads the record locked, so a note added meanwhile can't outlive it. A company with jobs refuses its delete, archived ones included (each keeps its posting from coming back), and counts them; its page lists them all.

## Page Tools

Claude works in the app only through its tools (KTD5). They're served from the app's MCP endpoint, signed in through Neon Auth's OAuth server (U18, KTD22), and registered as page tools (WebMCP) in Claude's own browser, the fallback until the endpoint has run a week (KTD6 as revised). Setting up both, and Claude's permissions: [docs/agent-access.md](docs/agent-access.md). The research behind the endpoint is in [docs/agent-mcp-research.md](docs/agent-mcp-research.md).
- **The MCP endpoint (U18, KTD22).** `app/(api)/mcp/route.ts` is stateless: the MCP SDK's web-standard transport (`@modelcontextprotocol/sdk` 1.x, which `@neon/oauth`'s types need) with a server per request (`app/_lib/agent-tools/mcp-server.ts`), answering JSON. It takes POST only. GET would open a stream for messages the server never sends, which on Vercel holds a function open until its time limit, and DELETE would end a session it doesn't keep, so Next answers both with 405, as MCP allows. A deployment that sets no `MCP_RESOURCE` serves no endpoint: `/mcp` and the discovery file answer 404, and `/agent` says so. Claude Code (2.1.278) opens each connection with a `server/discover` probe in protocol `2026-07-28`, which the SDK answers with a 400 before Claude Code falls back to the `2025-11-25` handshake. That's harmless, and it lasts until the SDK supports `2026-07-28`: its latest release, 1.32.2, stops at `2025-11-25` (checked 2026-11-09). `IMcpAuthService` (`neon-mcp-auth.service.ts`, over `@neon/oauth`; `mock-mcp-auth.service.ts` in tests, with `TEST_MCP_TOKENS`) checks the bearer token and serves the discovery file (`app/.well-known/oauth-protected-resource/[[...path]]/route.ts`); `IResolveTokenActor` acts only for `AGENT_USER_ID`. The endpoint serves every tool in the registry, its annotations in MCP's terms (`readOnlyHint` stays, `consequentialHint` becomes `destructiveHint`, `openWorldHint` is false, and MCP has no hint for outside text), and a call runs the page tool's own action inside `withTokenActor` (`app/_lib/current-actor.ts`), where `getActionActor` answers the token's actor and never reads the session. So a call answers, refreshes pages and logs as its page tool does, and a new tool needs nothing more than its registry entry. The sign-in and consent pages are `app/(auth)/auth/oauth/`, which Neon's OAuth server names as its login and consent pages; `next.config.ts` refuses their framing. App code can't import root `lib/` (the architecture lint), so the token check is a service in DI. The parity map gives the endpoint's methods `agentEndpoint`.
- `app/_lib/page-tools.ts` is the only module that touches `document.modelContext`, typed by hand from the W3C draft of 20 October 2026 as an optional property of `Document`. `registerPageTools(tools, signal)` registers each tool until the signal aborts (there's no `unregisterTool`), does nothing without the API, and drops the browser's expected refusals (`AbortError`, `InvalidStateError`), so none surfaces as an unhandled rejection. Any other refusal stays one, in the browser's console, rather than a tool that's quietly missing.
- A tool is one entry in `app/_lib/agent-tools/registry.ts`: a snake_case name of at most 30 characters, a generic description under 500 characters (R24), the JSON Schema (`z.toJSONSchema`, `io: "input"`) of the entity schema its controller parses with, its annotations (`readOnlyHint` on reads, `consequentialHint` on steps Claude Code asks about first, `untrustedContentHint` on results that can carry outside text) and its action. Adding, removing or changing a tool bumps `TOOL_SET_VERSION` (`src/entities/models/agent-session.model.ts`), which `whoami` reports, and lists the tool's schema in `tests/app/_lib/agent-tools/registry.test.ts`.
- `app/_components/agent-tools.tsx` registers every tool on mount and aborts on unmount, so the list is the same on every page. `ActorChrome` (`session-chrome.tsx`) renders it for Claude's session only. A call runs its action through `callAction` (`app/_lib/call-action.ts`) inside a transition, which answers with the action's envelope unchanged, `reload-needed` when the server no longer knows the action (a deploy since the page loaded, so nothing ran), or `unexpected` with "Couldn't reach the server" for any other throw: a tool that throws reaches Claude only as "invocation failed".
- The browser checks nothing against a tool's input schema: the controller's parse is the only check.
- Claude's page, `/agent`, gives the MCP endpoint's address (`IMcpAuthService`'s `resource()`) and lists the tools and Claude's latest changes, with no calendar and no auto refresh (KTD6). A write that changes what it shows revalidates it, as `start_session` does.

## Testing

- `tests/` mirrors the source tree (`proxy.ts` → `tests/proxy.test.ts`); run tests from this folder so `bunfig.toml`'s preload applies.
- The preload points `@/db` at PGlite, swaps `@/lib/auth/server` for a stand-in whose route handler records what reached Neon and whose `getSession` tells the auth page who's signed in (`tests/_support/neon-auth.ts`; set `neonAuth.answer` to make Neon fail or `neonAuth.session` to sign someone in, and `neonAuth.reset()` after), makes `redirect()` throw `Redirected` and `notFound()` throw `NotFoundPage` (`tests/_support/next.ts`), and stubs `next/font/google` for the root layout.
- Database: PGlite, an in-memory Postgres (`tests/_support/database.ts`), with the real migrations applied, so nothing in tests reaches Neon. Use-case and repository tests use `describeEachBackend` and `makeApp()` (`tests/_support/app.ts`, recipes' harness): each test runs on the mock repositories and on the real ones over PGlite, and one that fails only on `[postgres]` means a mock has drifted from the SQL. What only a database shows, such as a rollback, is tested on PGlite alone, with `resetDatabase()` in `beforeEach` and `sql()` for checks, never inside an open transaction (PGlite has one connection). A new table joins `resetDatabase`'s truncate list, or its rows carry over from test to test on `[postgres]` alone (U9's `weekly_reviews`, 2026-10-29).
- A test that writes a temporary folder (0011's migration test) makes it under `os.tmpdir()`. Inside Claude Code's sandbox that's `TMPDIR`, which Turborepo's strict mode withholds from a task that doesn't list it, and `tmpdir()` then falls back to `/tmp`, which the sandbox refuses (EPERM, 2026-11-10). So the root `turbo.json` passes `TMPDIR` to every app's `test` ([monorepo guide](../../docs/monorepo-guide.md#caching)).
- `RecordingLogger` (`tests/_support/logger.ts`) keeps every line logged at every level, so a test can show a value never reached the logs (KTD20).
- Who's signed in: `signInAs("owner" | "agent" | "stranger" | "signed-out")` (`tests/_support/session.ts`) sets the test container's `MockAuthService`. The container lives for the whole run, so every test that depends on the session calls it. Its mock repositories keep their rows for the whole run too, and the owner never changes, so a test that goes through the container works on records of its own (a fresh `crypto.randomUUID()`).
- Screen tests are `*.test.tsx`, as in recipes: `bunfig.toml` leaves them out of a plain `bun test`, `bun run test:screens` runs them with happy-dom (`tests/_support/dom.ts`), each file isolated, and `bun run test` runs both. Server components render with `renderOnServer` (`tests/_support/server-render.ts`): the tree streams as the server would send it, async components and `<Suspense>` included, into the page, and Testing Library's `within` finds things in it. What a component throws inside `<Suspense>`, such as a `redirect()`, goes to the `onError` a test passes it. Client components render with Testing Library's `render`, which runs their effects; `dom.ts` loads it once the document is in place and unmounts what it rendered after each test. `dom.ts` also gives Testing Library's waits (`findBy…`, `waitFor`) 3 seconds rather than 1, because CI's runners stall for about a second now and then. Fallow (3.36) follows that preload, so `dom.ts` needs no entry in `.fallowrc.json`.
- ICU builds format a date with a time differently: Bun on macOS says "Jan 5 at 2:00 PM", Bun on CI's Linux runner and Chrome "Jan 5, 2:00 PM" (2026-10-29). `formatMoment` formats the day and the time apart and joins them itself, so a screen test that asserts a moment passes on both. A new format that puts a date and a time in one `Intl.DateTimeFormat` call, as Claude's page's `WHEN` does, would need the same before a test asserts it.
- The preload stubs `next/cache` (`nextState.revalidated` in `tests/_support/next.ts` keeps the paths an action revalidated) and keeps Next's real `unstable_isUnrecognizedActionError` in its `next/navigation` stand-in, whose `useRouter` keeps where a screen went in `nextState.pushed` and whose `usePathname` reads `nextState.pathname` (`/` unless a test sets it). A test sets the window's width with `Object.defineProperty(window, "innerWidth", …)` before it renders the sidebar, which reads it to tell a phone from a laptop (`app-nav.test.tsx`).
- In screen tests, a `Button` rendered as a `Link` (`nativeButton={false}`) has the role `button`, not `link`, and a card `Item` that's a link is named by all its text. Testing Library's bound queries (`render(…).getByLabelText`) take no type argument: assert with `toHaveProperty("value", …)`. Fire `submit` at the form, never a button: React builds the form's data from the event's target, which happy-dom can't do for a button.
- A screen test of a toast renders `@repo/ui`'s `Toaster` with the id `APP_TOASTER` beside the component (one without the id shows none of the app's toasts), and calls `toast.dismiss()` after each test, since sonner's store outlives a render (`next-step-sheet.test.tsx`).
- `MockTransactionManagerService` runs one transaction at a time, as PGlite's one connection does, so two writes started together settle on the mocks as the database's locks settle them. Don't start a transaction inside another: on either backend it waits forever.
- Fixtures: `tests/_support/jobs.ts` makes companies and jobs through the use cases (both backends), and `tests/_support/screens.ts` through the actions, for screens. The test container keeps every record for the whole run, so a test names its own (a random suffix) and resets `nextState` after its setup.
- Page tools: `tests/_support/model-context.ts` is a fake `document.modelContext` that behaves as flag-enabled Chromium 156 did when measured (rejections, abort unregistering, results as JSON text). `setModelContext` gives the page one, or none, with a stand-in document in a plain test.
- Browser flows are `tests/flows/*.flow.ts`: Playwright's Chromium with `--enable-features=WebMCP`, run with `bun run test:flows`, locally only (not in `bun run test` or CI). `playwright.config.ts` starts its own `next dev` on 3301, never reused, which reads `.env`; the flows sign in as Claude's test-project account from `.env`'s `FLOW_AGENT_EMAIL` and `FLOW_AGENT_PASSWORD`. Next allows one `next dev` per folder, so stop a 3101 preview in the same checkout first. Chromium (`bunx playwright install chromium`) won't start inside Claude Code's sandbox (a ProcessSingleton error), so run the flows outside it.
