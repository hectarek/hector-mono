# How the features work

The rules for each of the app's features: what it does, where it lives, and what to keep true when changing it. They moved here from [AGENTS.md](../AGENTS.md) on 2026-10-01 so they load only when a feature is being changed; the rules every change follows stay in AGENTS.md. When a feature's behaviour changes, update its section here in the same change.

Paths are from the app's root; a bare file name is the only file of that name in the app.

## Recipes: ingredient lines, steps and scaling

- Ingredient lines: create and update run `toLineWrites`. A line from the editor arrives as its fields, with `raw` (its original line) only while the row is untouched; a changed or new row gets `raw` written out from its fields (`lineText`). A line given only as `raw` (imports, the seed, tests) is itemized with `itemizeLine`. On an update, a line keeps its catalog link while its name is unchanged (the recipe's current lines are the `links`); otherwise the repository upserts its `catalogName` (`toCatalogName` of the name). Copies (adopt) carry lines and steps over as stored, with their `ingredientId`.
- Steps: the editor sends them (`steps`); the Obsidian seed splits a note's markdown method into steps (`toStepWrites`). A step may carry a `section` (D35). Split text turns a heading step (bold only, like "**Sauce:**", a markdown heading, or a short plain line ending in a colon, like "For the sauce:") into the section of the steps after it (`withSections`); a heading line is its own step even with no blank line around it (`startsSection`: a bold one always, a plain colon line only where a paragraph could start, so a wrapped sentence ending in a colon stays whole; a list item ending in a colon is the item, its marker dropped). Bold text that ends like a sentence ("**Don't overmix!**") is a step, not a heading, and plain "Step 2:" labels are dropped like "### Step 2". A heading with no step of its own stays a step. The recipe page and cook mode show a section's heading once over its run of steps (`stepGroups`), with numbering running on.
- A line shows from its fields (`showLine` in `scaling.ts`, rendered by `LineText`): "3 cloves garlic", then the note and "optional" in a quieter voice. A line with no name (never itemized) falls back to its original text through `scaleLine`.
- After a measuring unit (`MEASURE_UNITS`, `ingredient-line.ts`), a bracket or slash measure is the same amount again ("2 tablespoons (30 ml) olive oil", "1¾ cups/225 grams flour"): `itemizeLine` leaves it out of the name (it stays in `raw`). After a package unit it's the size and stays ("crushed tomatoes (14 ounces)"). A size written before its can or package, unbracketed ("1 15-oz. can chickpeas", "28-ounce can tomatoes", one can), is read as the bracketed form (`bracketPackageSize`). "2-2/3 cups" is two and two-thirds, not a range.
- Parser fixtures in `tests/src/entities/ingredient-line.test.ts` are real lines from the Obsidian vault. When the parser misreads a real line, add that line as a test case before fixing it.
- Copying ("adopt") creates independent recipes with `copied_from_recipe_id` set; lines and steps are copied as stored, not split again. If any requested recipe is gone, nothing is copied.
- Scaling a line with fields multiplies its amount and picks the unit's singular or plural (`unitLabel`, `scaling.ts`). For a line without fields, `scaleLine` rewrites the leading amount and, after a measuring unit only, the bracketed alternate measure ("110 g (⅓ cup)" → "220 g (⅔ cup)"). Brackets after package units are sizes ("1 can (14 oz)") and never scale.
- Unit words and their plurals (`UNIT_WORD_FORMS` in `ingredient-line.ts`) are the one list both scaling ("1 cup" → "2 cups") and grocery-line text use.

## Library and tags

- The library's search (docs/ux-plan.md P10.4): the page fetches every card the tag allows, and `LibraryResults` (client) narrows them as you type with `matchesSearch` (`src/entities/library.ts`, the same rule `buildLibraryView` uses), updating `?q=` with `window.history.replaceState` (no reload, no new history entry). Its search starts from `useSearchParams`, not the page's props: Back to a search typed in place returns the page as loaded before it. The search box is still a GET form and the chips links (`libraryHref`, `app/_lib/library-href.ts`), and the server render applies `?q=`, so a shared link or a browser without the script gets the same results.
- Tags are normalized (trimmed, lowercased, deduped) in the Zod schema, so they only get normalized when input passes through a controller.
- The library list (`getBySpace`) returns recipe rows without ingredient lines; only the detail view loads lines.
- All recipes (`?book=all`, `ALL_RECIPES` in `load-books.ts`) is `getAllRecipes`: every book the user is in, merged by title, with tags counted across them. Being in a book is its access check, so it reads only the user's own memberships. The "All recipes" pill shows when they're in two or more books.
- A new recipe's book: the one it was started from, or from All recipes their own (the oldest book they own). The form shows a Book picker when they can edit two or more books.
- Tags in the recipe form (new and edit) are chosen, not typed (docs/ux-plan.md D33): `TagPicker` shows the tags from every book they're in (most used first) and the recipe's own as chips, plus **New tag**, a box whose text is tidied and lowercased, and which picks an existing chip rather than adding a copy (`app/_lib/tag-choices.ts`). The form sends them as the same comma-joined `tags` field, with any tag typed in New tag but not yet added. Nothing is written until Save.

## The recipe form

- The recipe form's ingredients and method are rows (docs/ux-plan.md P9.4): `IngredientRows` (amount, unit, name inline; note and optional in the ⋯ sheet; section rows head the lines below them) and `StepRows` (text; timer in the ⋯ sheet; section rows too, D35, using `IngredientRows`' `SectionItem`), sharing `RowSheet` (fields, then Move up/down, Remove, Done; changes apply as made). The row logic is pure in `src/entities/editor-rows.ts`. Pasting a list with line breaks into a row adds a row per line (the text split); `pasteRows` places them, and when they bring sections, starts the section the rows after them were in again, so those don't move. On Save, the form checks the rows (`ingredientInputs`, `stepInputs`; a named section with nothing under it is a problem, not dropped), puts the cursor on the row with a problem, and sends them as JSON (`ingredients`, `steps`). Return in a one-line field never submits the form (`keepTyping`): Save is its submit button, so it would save mid-edit. Return that confirms an IME's text is left alone (`isComposing`, or Safari's keyCode 229). Each section's rows are their own list after the section's name (`rowRuns`; steps' lists numbered on with `start`), so a screen reader counts only lines or steps; a row moved across a section moves to another list. After Remove the cursor goes to the neighbouring row's ⋯ (`useRowMenus`), not its text field, so no keyboard comes up. Row keys stay out of the DOM (the server's and the browser's differ); inputs are found through a key-to-element map.
- The recipe form is four groups with a `FieldSeparator` between them (docs/ux-plan.md P12.3): the recipe (Book, Title, Description, Servings and Time, Source and Photo links), Ingredients, Method, Tags. `FIELD_ORDER` lists the fields in that order, since a failed save focuses the first one with a problem. Under the ingredient rows and the steps: a `Separator`, then their add buttons side by side at half width.
- The recipe form warns before losing typing: Cancel asks ("Discard your changes?") and `beforeunload` prompts once it's changed. The iOS back swipe can't be caught by a page (H7 in `docs/ux-plan.md`).

## Spaces, invites and defaults

- `ensurePersonalSpace` re-checks under a Postgres advisory lock (`lockOwnerScope`) so concurrent first loads create one space.
- The owner's name for a new personal book or plan comes from Neon Auth's `neon_auth.user` (`getUserName`, docs/ux-plan.md D19): `personalSpaceName` makes it "Hector's Recipes" / "Hector's Plan" from the first word, or "My Recipes" / "My Plan" for an account with no name. In tests, set a name with `app.nameUser` (works on both backends).
- Invites: joining is always an explicit POST (Join button), never on page load, because link previews and prefetchers GET URLs. Accepting never changes an existing member's role.
- Joining a plan (`accept-invite.use-case.ts`, docs/ux-plan.md D15), only when they weren't in it already: their own plan is deleted if it's untouched (`isUntouchedPlan`: no entries, no grocery items, no one else in it, no live links), and the joined plan becomes their default when they had no plan, theirs was replaced, or they ticked "Make it my default plan". The join screen shows that box only when their own plan is in use (`InvitePreview.ownPlanInUse`).
- Someone who owns no plan gets "Start my own plan" in the plan's ⋯ sheet (`startOwnPlan`: their personal plan, made their default).
- Defaults: `listForUser` marks the space of that type the person chose (`isDefault`, from `user_settings`; a space they've left simply isn't listed), and `pickDefaultSpace` takes it first, else a shared one beats their own. So every page and picker follows the choice with no extra query. `setDefaultSpace` saves it: any member may choose, and null clears it. The library opens to the default book, else All recipes when they're in two or more books.
- Meal plans: which plan shows by default is `pickDefaultSpace`. `app/_lib/load-plans.ts` (the Plan and Groceries tabs) only creates a personal one when the user is in none, so joining a shared plan never leaves an empty one behind. Books always get a personal one (`load-books.ts`).
- Pickers of where to add something (a plan, or whose list) use `editableSpaces` from `space.model.ts`: editable spaces only, default first. `resolvePlanId` uses the same helper, so the picker's first option and the no-picker default always agree.
- Sentences about joining or deleting a space use `SPACE_TYPE_CONTENTS` (`app/_lib/space-href.ts`), which says a plan comes with its grocery list; `SPACE_TYPE_LABELS` is the short name for headings.
- Choosing defaults: `DefaultBookPicker` on the Books page (a select that saves on change; "All recipes" is the empty value) and `MakeDefaultButton` in a plan's ⋯ sheet when you're in two or more plans.
- Inviting is **Invite** in a space's ⋯ sheet, for owners (`SpaceMenu`, `space-menu.tsx`; docs/ux-plan.md D20, D42): it turns the sheet into Can edit / View only, each sharing that role's link through `ShareLinkButton` (native share sheet, else copy). The links are fetched when Invite is tapped (`inviteLinks` → `ensureInviteLinks`: the newest live link per role, or a new one), not when the sheet opens, so opening it for Members makes no links; and not at share time, because iOS only opens the share sheet straight from a tap, never after an await. Turning links off stays on the members page.

## Plan

- Picking a day is `DayPicker` (`app/_components/day-picker.tsx`): the next seven days from today as buttons (`upcomingDays`), plus Other for the date input. Pass it the server's `todayIn(PLAN_TIME_ZONE)`.
- A meal's days (Add to plan, and Change days in a meal's ⋯ sheet; docs/ux-plan.md D38) are `MealDaysPicker` (`app/_components/meal-days-picker.tsx`): **Cook on** (`DayPicker`), then **Eat on**, toggle buttons for the week from the cook day (the cook day selected to start) plus Other for a later day. Moving the cook day moves the eat days with it (`moveCookDay`, `src/entities/meal-days.ts`, which also has `toggleEatDay` and `mealDaysText`, "Cook Sun 4 · eat Sun 4, Mon 5 and Tue 6"). Save stays off with no eat day; the server holds the rest (none before the cook day).
- Plan entries copy the recipe title when added (`recipe_id` is set null if the recipe is deleted). Entries can come from any book the user is in; everything on a plan comes from a recipe (D40). A week's plan is every meal cooked or eaten in it (`listForRange`), so a Sunday cook eaten on Monday is in both weeks. Changing a meal's days (`changeEntryDays`) keeps everything else, cooked and added-to-list included. The week shows a linked recipe's current title (`getWeekPlan` looks them up with `getByIds`); the saved copy is for a recipe since deleted.
- The week view (`PlanWeek`, docs/ux-plan.md P13.4) lists each day's meals with `mealsOnDay` (`src/entities/meal-days.ts`): on its cook day a meal has a pot, "Cook" (and "eat Mon 5, …" when it isn't eaten that day) and the plan's only check, cooked (D39); on a day it's only eaten it's lighter, with "Cooked Sat 3", and its sheet can take that day off the meal (D43, `canTakeDayOff`: never the meal's only eat day). Days before today have muted text; their controls stay full strength. Dates a week or more from today carry their month (`shortDay`: "Thu Oct 8", D47; the eat-day buttons go to three columns to fit them). There's no per-day add: planning starts from a recipe (D40), and Plan's "Plan a meal" opens Recipes.

## Groceries

- Grocery adds (one recipe, or a plan's meals) all go through `src/application/use-cases/grocery/add-recipe-lines.ts`: scale to servings, plan the batch against the list's unchecked items, write in one transaction. Same ingredient + same unit merges; an amount-less line ("Salt, to taste") already on the list is skipped; checked items are never merged into.
- The plan's grocery button (`addPlanToList`, docs/ux-plan.md D41, D44, D45) adds the meals with a recipe, not cooked and not added, cooking in a range from today (`listNotAdded` with `groceryRangeDays`: next 3, 7 or 14 days, or all upcoming). `listMealsToAdd` gives Plan their cook days, and the button counts the ones in the range picked. With an `entryId` it adds that one meal, whatever its day ("Add to grocery list", then "Add to list again" for a second batch). Every meal it handles is marked (`added_to_list_at`); a cook row shows a cart once its meal is marked. The meal is read inside the transaction, after the lock (`getById(id, tx)`), and the sheet says which button was pressed (`again`): a first add of a meal already on the list (a sheet that's out of date, two presses at once) adds nothing.
- Adds to one list take turns: both recipe adds start their transaction with `lockList` (a transaction-scoped advisory lock), so two people pressing at once can't both read the list before either writes.
- No double-adding: a recipe is "already on this list" when unchecked items there name it in their "for …" note (`recipesOnList`), and a plan entry is already added when `added_to_list_at` is set. A recipe's own Add to list leaves out one already on the list unless asked again (`again`). For planned meals (D45), a recipe on the list covers one meal of it, the earliest, only when no planned meal of it that's added and still to cook (not cooked, cooking today or later) exists (`addedRecipeIds`): otherwise the items are that meal's, and the next cooking is a second batch. Past meals don't count, since their items were bought. Both report `alreadyAdded`. The note holds the recipe's title when it was added, so a recipe renamed since isn't recognised (its items would be added again), and two recipes with the same title count as one (a planned one is taken as on the list when the other is). Only a plan editor marks entries as added (viewers can't change a plan).
- Recipe lines go onto the list from their fields (`toGroceryLines`): the amount, unit and name, never the note, and never an optional line (D23, D25). The name's last word is made singular first (`singularName`), so `formatGroceryText` counts it right ("1 onion" doubled is "2 onions"); a name with brackets stays as written. A line with no name falls back to `groceryText`, the recipe's own words minus the note, which only cuts at a comma when the next word is in `NOTE_WORDS`. When a real line comes out wrong, add it to the tests before changing the rule.
- The grocery list groups what's left to buy by aisle (`groupByAisle`, `src/entities/aisles.ts`), in store order with "Other" last, once any item has an aisle. An item's aisle is its catalog ingredient's (the repository joins `ingredients`); the mock has no catalog, so aisle tests run on Postgres.
- Editing a grocery item (`updateText`) makes it plain text, like a typed-in item: amount, unit and ingredient are cleared (the "for …" note stays), so nothing merges into a number the text no longer shows.
- Grocery items are ordered by `created_at`. Every insert takes its stamp from `nextCreatedAt` (now, or just after the newest item on the list, whichever is later), and a batch steps it per row so a recipe's ingredients keep their order. A typed item used to take the database's `now()` and could land among a recipe's lines stamped a moment ahead (a test flake, fixed 2026-09-30). Keep every insert on `nextCreatedAt`.
- Whose list a recipe's "add" goes to is resolved in `app/actions/grocery.ts` (`resolvePlanId`): the default plan you can edit, else your own (created if needed). A plan's meals always go onto its own list, so adding them needs edit rights on that plan.
- Grocery check/uncheck/remove go further: `usePendingWrites` (`app/_lib/use-pending-writes.ts`, logic in `pending-writes.ts`) queues a tap that can't reach the server in `localStorage` and retries it on `online` / visible / mount, so it works in a store with no signal. Queued writes set values (never toggle), so a late or repeated send is harmless; the row shows "Not saved yet". Adding an item still needs the server and says so. `AutoRefresh` skips while `navigator.onLine` is false: Next.js answers a failed `router.refresh()` with a full page load, which offline is the browser's error page.

## Live updates

- Live updates (docs/ux-plan.md D21) go through `IRealtimeService`. `AblyRealtimeService` is the only server file that imports `ably`; in the browser it's `app/_lib/live-updates.ts`. `AblyRealtimeService` takes its client as a constructor argument, so tests pass a stand-in, and `null` means no key (live updates off). Channels are per plan (`planChannel` in `src/entities/realtime.ts`), and a message only says "changed". Grocery write use cases call `listChanged` after their write commits, and only when the list changed (clearing nothing, or adding a recipe that's already there, publishes nothing). A failed publish is logged, never thrown. Tests check what was published through `app.realtime.published` (both backends).
- `LiveList` (`app/_components/live-list.tsx`) is the browser side, through `listenToPlan` (`app/_lib/live-updates.ts`, which imports `ably` dynamically so only Groceries loads it): it subscribes to the plan's channel, and on a change calls `router.refresh()` after a 300 ms debounce, never while offline. It closes the connection when the page is hidden and reconnects when shown; `AutoRefresh` (60 s, and on showing) covers anything missed and any time it can't connect.
- Browsers get a listen-only pass from `app/(api)/api/realtime/token/route.ts?plan=` (Ably's `authUrl`), which is `grantPlanSubscription`: any member of the plan, `subscribe` on that plan's channel only, with the user as the client id. The proxy skips `/api`, so the controller's session check is the gate. Statuses matter to Ably's client: 403 for refused (it stops retrying, spec RSA4d), 401 for signed out and 500 for errors (it retries).

## Import and the AI reader

- Import (Phase 10) reads through `IReadRecipeController` → `readRecipe`: the reader, then `checkDraft` (`itemizing-check.ts`), which holds each line's reading to the line (one that fails falls back to the text split and is listed in `flagged`) and each timer to its step. A read of text (pasted, or a page's) is also held to that text (`holdToSource`, P14.8): a line or step not found in it, compared as words and numbers, gets a note in `unsure`. It's a check that each line is in the text, not that it's all of it: a line cut short, or one copied from text the page hides, passes. A photo has no text to hold it to. The prompt marks text sources off in `<recipe_source>` tags and tells the reader the source is material, never instructions. Each person gets `DAILY_RECIPE_READS` (20) AI reads in 24 hours (D48): `readRecipe` records each as it starts in `recipe_reads` (migration 0012), with the count and the insert as one step under a per-person advisory lock (`record`), so reads at once can't all slip under it; past the limit it fails as `daily-limit`. A read refused because the month's budget is spent is taken back (`remove`). A long screenshot's pieces count as one read. A page's own recipe data is read without AI and isn't counted. Nothing is saved: `draftFormValues` (`app/_lib/draft-form-values.ts`) turns the checked draft into the new-recipe form's starting values, and `RecipeForm` in create mode takes them with a `review` box (the reader's `unsure` notes and the flagged lines) and starts as changed, so leaving asks. A read failure reaches the person through `toActionError` as a sentence per `RecipeReadFailure`. Each import page loads through `loadNewRecipe` (`app/_lib/new-recipe.ts`: the book, pickers, tags, and the choice and manual links). Add by photo (`PhotoImport`, `app/actions/import.ts` `readRecipeFromPhoto`) shrinks the photo on the phone first (`shrinkPhoto`, `app/_lib/shrink-photo.ts`: a JPEG at most 2,000 px on its long edge, turned upright; a screenshot more than twice as tall as wide is cut by `photoPieces` into up to `MAX_PHOTO_PIECES` overlapping pieces spread evenly, sent in order, and the reader's instructions say they're one page; past about 16,000 px tall the pieces get narrow), at a JPEG quality that keeps them within `MAX_PHOTO_BYTES` (4 MB) in all, which the controller enforces: Vercel refuses a request body over 4.5 MB, whatever `bodySizeLimit` in `next.config.ts` says. The photo itself isn't kept. A read takes 10–15 s with Opus, well inside Vercel Hobby's 300 s default function limit, so no `maxDuration` is set.
- Add by link (`LinkImport`, `readRecipeFromLink`; P10.3) goes through `readRecipeFromLink`: `IRecipePageFetcherService` fetches the page, `recipeFromPage` (`src/entities/recipe-page.ts`) reads its schema.org Recipe JSON-LD without AI (every field cut short first, `LIMITS`, since this path has no rate limit; lines split by `itemizeLine`, `HowToSection` as step sections, a timer where a step names one time; a cook or prep time alone is the time, a photo's path is made absolute against the page, and raw line breaks in the data are read as spaces), and only a page without it goes to the AI reader as `pageText` (capped at 30,000 characters; a page with no text fails as no-recipe-found without a read). `HttpRecipePageFetcherService` is the only file that fetches the web: http(s) on ports 80/443, every address a name resolves to checked as it connects (`isPublicAddress`, `public-address.ts`; an address typed into the link is checked before), redirects followed by hand and checked again (at most 3), 8 s, 3 MB, HTML only (decoded in the charset its header names, else its `<meta charset>`), no cookies, and a user agent that names the app (never a browser's). Its failures are `PageFetchError` reasons, each a sentence in `toActionError`; the link screen then offers pasting the text (`readRecipeFromText`), a photo, or the form. Its tests run a local server behind fake names (`resolve`, `isAllowedAddress`, `ports` options). A line's suggested `aisle` rides on its row (`LineRow.aisle`) until its name changes, and is saved for the catalog ingredient.
- Reading recipes with AI (D26, D27, D29, D30) goes through `IRecipeReaderService`. `read(source)` transcribes text or an image into an itemized `RecipeDraft` for review (import, Phase 10). Nothing is saved by the reader. A schema only holds the model to a shape: hold its values to the source with `checkLineReading` / `checkTimer` (`src/entities/itemizing-check.ts`), where a line that fails any check keeps the text split whole and is flagged. The reader returns the model's words only trimmed; `checkLineReading` names the shopping item with `toCatalogName`. Never name one by parsing it as a line (`parseIngredientLine`), which reads unit words: "ground cloves" would become "ground". Keeping the reader's answers raw means a naming or check fix never needs the recipes read again. `AiGatewayRecipeReaderService` is the only file that imports `ai` / `@ai-sdk/gateway`. It uses AI SDK 7 `generateText` with `Output.object`, and `instructions` (v7's name for the system prompt). Its model comes from `ai-gateway-models.ts` (Opus 5.5, `anthropic/claude-opus-5.5`, docs/ux-plan.md D36) and is a constructor argument, so tests pass `MockLanguageModelV4` from `ai/test`. The schema sent to the model has no numeric or length limits, and `toDraft` enforces them. Failures become `RecipeReadError`: 402 from the Gateway (budget or credit spent) is `budget-paused`. Log errors through `describe(err)`, never the error object: the SDK's errors carry the whole request, a photo included. `ai` is pinned to the exact version whose `@ai-sdk/gateway` pin we also depend on, so upgrade them together.

## Cook mode and servings

- Cook mode wake lock (`app/_lib/use-wake-lock.ts`): re-requested whenever the page becomes visible and on the next tap after a refusal (some browsers require a user gesture). Unsupported/refused shows a notice rather than failing silently. The Claude browser pane always refuses the permission, so verify on real phones.
- Step timer alarm (`app/_lib/alarm.ts`): Web Audio, made and resumed in the tap that starts a timer (iOS won't start a context outside a tap), kept running while a timer runs, and suspended when the last one stops. Timers restored after a reload have no sound until a tap, so cook mode primes it on the next tap anywhere (`useSoundNeedsTap` in `app/_components/cook-mode.tsx`: pointerup, touchend, click, or a key other than Escape or a shortcut) and says so under the running timer. Safari plays Web Audio as ambient sound, which the silent switch mutes, so `primeAlarm` sets `navigator.audioSession.type = "playback"` before the context exists; playback doesn't mix, so another app's music pauses while a timer runs. iPhone has no `navigator.vibrate`. The silent switch can only be checked on a real phone.
- Cook mode keeps your place (crossed-off ingredients, current step) in `sessionStorage` per recipe (`useCookProgress` in `app/_components/cook-mode.tsx`; what's stored, and how it's read back, is `app/_lib/cook-progress.ts`), restored after mount; servings live in the URL instead. Opening on saved progress shows "Picked up where you left off" with Start over.
- Cook mode steps: the stored steps (`recipe_steps`). A step's tap target is an empty button *behind* its content, never around it, because the content holds links and the timer button, and a button can't hold either. Under each step, the lines it uses (`stepIngredients`: a line's name in the step's text, or an ending of it that no other line shares).
- Cook mode timers: a step with `timer_minutes` offers one. It counts down in place, is kept with the cook progress (its end time, in `sessionStorage`), and beeps when it ends while the page is open (`app/_lib/alarm.ts`; `primeAlarm` runs on the tap that starts it, since iOS allows sound only after a tap). It buzzes only once the page has had a tap, and a timer that ended long before the page opened doesn't ring.
- A recipe's servings are one value per screen: `RecipeServings` (`app/_components/recipe-servings.tsx`) wraps the recipe page and cook mode, and the stepper, `AddToListButton` and `CookLink` all use it. Cook mode takes `?servings=` and keeps it in the URL. Change servings with the updater form (`setServings((value) => value + 1)`), so quick taps each count.
